# 데이터 재배치를 지원하는 소형 DB 샤딩 시스템 — 프로젝트 기획서

작성일: 2026-10-28

이 문서는 최초 요구사항과 이후 논의한 장비 구성, 백업, 장애 대응, 팀 작업 방식을 정리한다. **현재 구현된 기능과 앞으로 구현할 계획을 구분한다.** 구체적인 알고리즘·숫자·운영 정책 중 아직 합의하지 않은 내용은 제안 또는 미정으로 표시한다.

## 1. 프로젝트를 한 문장으로 설명하면

가상 주문 데이터를 여러 PostgreSQL DB에 나누어 저장하고, **기존 데이터와 요청의 정확성을 지키면서 특정 버킷을 다른 장비의 DB로 옮기는 시스템**을 만든다.

핵심 성과는 안전한 재배치, 중단 후 복구, 실제 데이터 검증이다. 별도 장비를 사용한 성능 변화는 실험으로 확인한다. 실제 쇼핑몰 서비스나 모든 상황에서 더 빠른 DB를 만드는 것이 목표는 아니다.

## 2. 현재 상태와 개발 원칙

현재 활성 코드는 Java·Spring Boot 기본 프로젝트다.

- Java 21, Spring Boot 4.1.1, Gradle 9.8.1 Wrapper를 사용한다.
- 애플리케이션 실행 클래스, `GET /health`, 기본 설정과 헬스 체크 테스트가 있다.
- 활성 코드에는 JDBC 연결, 주문 API, 샤딩, 재배치, 백업 기능이 아직 없다.
- 이전 구현은 `.local/backups/`에 보관되어 있다. 이것은 **소스 코드 보관본**이며, 이번에 설계하는 **DB 운영 백업**과 다르다.
- 남겨 둔 DB 볼륨의 현재 실행 상태와 데이터는 이번 문서 작업에서 검증하지 않았다.

이 문서 작성으로 코드를 이전 구현 상태로 복원하거나 다음 기능을 자동으로 구현하지 않는다. 기존 기본 코드에서 작은 작업 하나씩 다시 진행한다.

## 3. 하드웨어와 시스템 구성

| 위치 | 구성 | 역할 |
| --- | --- | --- |
| 내 PC | Spring Boot 애플리케이션 1개 | 요청 처리, 해시 계산, 라우팅, 재배치 제어 |
| 내 PC | 메타데이터 PostgreSQL DB | 샤드 목록, 버킷 소유권, 작업 진행 상태 저장 |
| 내 PC | PostgreSQL 샤드 A·B | 초기 주문 데이터 저장 |
| 학교 강의실 PC 후보 | PostgreSQL 샤드 C | 재배치받은 버킷의 실제 주문 데이터 저장 |
| 내 PC의 지정 폴더 | 외장하드 대체 백업 저장소 | 정상 시점의 백업 세트 저장 |
| 백업과 구분한 지정 폴더 | 장애 기록 저장소 | 로그, 상태 기록, 수집 가능한 장애 시점 덤프 저장 |

학교 PC는 설치·사용 허가, 데이터 보존, 네트워크 연결이 확인된 후 C 장비로 확정한다. 학교 PC에는 DB 실행 환경이 필요하며, Java·IntelliJ·React를 모두 설치할 필요는 없다.

초기 개발은 한 PC에서 기능을 확인하고, 이후 C의 연결 설정을 바꾸어 실제 두 장비로 실험한다. 각 DB의 데이터는 독립적인 영속 볼륨으로 관리한다.

**A·B는 같은 하드웨어를 공유한다. C는 복제본이나 대기용 백업 DB가 아니다.** 이동이 끝난 버킷은 C가 담당하고, A 또는 B의 이전 복사본은 검증 후 정리한다. C가 중단되면 C 담당 버킷을 자동으로 A·B에서 처리할 수 있다고 가정하지 않는다.

애플리케이션과 메타DB도 내 PC에 있으므로 이 PC가 꺼지면 전체 서비스에 영향이 생긴다. 이번 구조는 자동 장애 전환이나 고가용성 구성이 아니다.

## 4. 다른 장비에 C를 두는 이유

1. **데이터가 있는 상태에서 저장 장비를 확장하는 과정**을 보여준다. 처음부터 세 DB에 나누는 것과 달리, 기존 버킷을 추가 장비로 옮긴다.
2. **별도 CPU·메모리·디스크를 활용할 수 있는지** 확인한다. 같은 PC의 컨테이너 수만 늘린 실험과 구분한다.
3. **실제 네트워크와 장비 장애를 다룬다.** 지연, 연결 단절, C 종료·재시작 후의 상태와 복구 동작을 검증한다.
4. **성능과 이동 비용을 함께 측정한다.** 부하 분산 효과뿐 아니라 복사 시간, 쓰기 제한 시간, 원격 통신 비용도 기록한다.

병목 확인은 이 실험의 한 부분이다. 성능이 개선되지 않아도 데이터 정확성, 확장 과정, 원인 분석이 재현 가능하면 의미 있는 결과다. 특정 사용자에게 요청이 집중되면 그 사용자의 버킷을 옮겨도 요청 자체가 여러 샤드로 쪼개지지는 않는다.

요청 처리, 업무 규칙, 버킷 계산, 매핑 조회, 샤드별 SQL, 재배치 처리를 구분한다. 다만 기능이 생기기 전에 빈 클래스나 범용 프레임워크를 대량으로 만들지 않는다.

PostgreSQL 및 관련 도구의 실제 버전은 DB를 다시 구성할 때 호환성을 확인하여 고정한다. 이번 문서의 PostgreSQL 기술 근거는 18 버전 공식 문서를 참고했다.

## 6. 버킷과 라우팅

기본 버킷 수는 **16개**, 번호는 **0~15**다.

요청 흐름은 `user_id → 결정적 해시 → bucket_id → 메타DB의 현재 소유 샤드 → 해당 DB의 SQL 실행`이다.

- 같은 사용자 ID는 재시작하거나 PC를 바꿔도 같은 버킷으로 계산한다.
- 초기에는 A·B가 모든 버킷을 나누어 맡고 C는 재배치 대상이다.
- 예를 들어 A가 0~7, B가 8~15를 맡을 수 있다. 이 구간 배치는 초기 매핑 제안이며 아직 확정 SQL은 아니다.
- 재배치에서는 해시와 버킷 번호를 유지하고 담당 샤드만 바꾼다.
- 해시가 사용자 수를 잘 분산해도 데이터 건수와 요청량까지 균등해지는 것은 아니다.

구현 전 해시 알고리즘, 입력 형식, UTF-8 인코딩, 정수 해석과 나머지 연산 규칙을 확정한다. 음수·오버플로를 처리하고 고정 테스트 벡터로 검증한다. 과거에 검토한 구체적인 해시 방식은 재검토할 설계안이며 이 문서에서 확정하지 않는다.

`orders.bucket_id`를 단순히 `user_id % 16`으로 생성하면 새 해시 규칙과 충돌한다. 애플리케이션 계산값 저장과 검증 방식 또는 DB의 동일 해시 구현 중 하나를 설계 단계에서 선택한다. 테스트 데이터 생성기와 독립 검증 도구도 같은 명세를 따른다.

## 7. 데이터 모델과 주문 기능

설명용 그림: [사용자·버킷·샤드와 주문 튜플](images/01-user-bucket-shard-tuples.png), [테이블 구조·튜플 예시·키 관계](images/02-table-schema-and-tuple.png). 그림의 데이터와 상태값은 예시이며 실제 DB 조회 결과가 아니다. 같은 이름의 SVG 파일도 편집 가능한 원본으로 보관한다.

| 저장 위치 | 테이블 | 주요 내용 |
| --- | --- | --- |
| A·B·C | `orders` | `order_id`, `user_id`, `bucket_id`, `amount`, `status`, `created_at`, `updated_at` |
| 메타DB | `shards` | 샤드 식별자·이름, `connection_key`, 상태 |
| 메타DB | `bucket_mapping` | 버킷, 현재 담당 샤드, 상태, 매핑 버전 |
| 메타DB | `migration_jobs` | 버킷, 출발·도착 샤드, 단계, 체크포인트, 검증 결과, 오류, 시각 |

주문 ID는 애플리케이션에서 생성하는 UUID다. 사용자 ID와 주문 ID는 생성 후 바꾸지 않는다. 금액은 Java `BigDecimal`과 PostgreSQL의 정확한 소수형을 사용한다. 정밀도, 허용 범위, 주문 상태와 상태 전이, 시각 저장·표시 기준은 상세 스키마에서 확정한다.

메타DB 내부의 매핑·작업·샤드 관계에는 외래키를 둔다. 서로 다른 DB 사이에 외래키가 적용되는 것처럼 설계하지 않는다. `orders.user_id`는 가상 주문의 소유자이자 라우팅 기준이며, 회원 테이블의 외래키가 아니다. 관리 화면의 로그인 계정과도 별개다.

`shards.connection_key`는 서버 설정을 찾는 키다. DB 비밀번호와 실제 연결 비밀정보를 메타 테이블이나 Git에 저장하지 않는다.

구현할 주문 기능은 다음과 같다.

- 주문 생성, 사용자별 목록·상세 조회, 금액·상태 수정, 실제 행 삭제.
- 주문 취소는 상태 UPDATE로 처리하고 실제 DELETE와 구분.
- 전체 주문 조회·집계와 올바른 전체 정렬·페이지 처리.
- 잘못된 입력, 없는 주문, 샤드 연결 실패, 재배치로 인한 요청 제한에 대한 명확한 응답.

복사 중에는 같은 주문이 두 DB에 물리적으로 존재할 수 있다. 조회·집계는 **현재 소유 샤드의 행만** 사용해 논리적 중복을 막는다. 일부 샤드가 실패하면 불완전한 전체 결과를 성공으로 반환하지 않는다. 매핑 변경은 버전으로 감지하고 안전한 조회만 제한적으로 재시도한다. 여러 DB의 동시 변경을 하나의 전역 시점으로 읽는다고 보장하지 않는다.

## 8. 안전한 버킷 재배치

초기에는 관리자가 이동할 버킷과 목적지를 선택하며, 전체 시스템에서 미완료 재배치 작업을 한 개로 제한한다.

| 순서 | 수행 내용 | 지켜야 할 조건 |
| --- | --- | --- |
| 1 | 버킷, 출발·목적지, 매핑 버전과 미완료 작업 확인 | 잘못되거나 겹치는 작업 거부 |
| 2 | 해당 버킷의 새 쓰기 제한, 기존 쓰기 종료 대기 | 실제 DB 트랜잭션의 커밋·롤백 완료 확인 |
| 3 | 데이터를 작은 배치로 복사 | 읽기는 아직 출발 샤드 사용 |
| 4 | 목적지 커밋 후 체크포인트 기록 | 기록만 앞서 나가 데이터가 빠지지 않도록 순서 보장 |
| 5 | 주문 ID, 건수, 체크섬, 필드 내용 검증 | 불일치하면 소유권 전환 금지 |
| 6 | 해당 버킷의 새 읽기도 잠시 제한, 기존 읽기 종료 대기 | 이전 소유권으로 실행 중인 요청 정리 |
| 7 | 메타DB 트랜잭션으로 소유권·버전·작업 단계 변경 | 소유권 판단의 기준을 한 번에 갱신 |
| 8 | 목적지 재검증 후 요청 재개 | 새로운 담당 샤드로 라우팅 |
| 9 | 출발 샤드의 해당 버킷 이전본 정리 | 다른 버킷과 목적지의 새 데이터 보존 |

다른 버킷의 요청은 계속 허용한다. 다만 CPU·디스크·연결 풀을 공유하므로 성능 영향이 전혀 없다고 주장하지 않는다. 요청 제한의 응답 코드, 재시도 안내와 대기 시간 상한은 API 설계에서 정한다.

버킷별 요청 제어, 메타DB 행 잠금, 미완료 작업을 제한하는 인덱스, 매핑 버전 비교를 함께 사용한다. 잠금 하나나 인덱스 하나로 모든 경합이 해결되지는 않는다. **서로 다른 DB의 복사와 소유권 전환을 하나의 원자적 트랜잭션으로 취급하지 않는다.**

같은 복사 배치를 다시 실행할 수 있어야 한다. 이미 존재하는 주문 ID는 필드까지 비교하며, 무조건 덮어쓰거나 충돌을 무시해 다른 데이터를 숨기지 않는다.

## 9. 평소 백업: 외장하드 저장을 로컬 폴더로 실습

### 9.1 합의한 방식과 실습의 경계

정상 운영 중 복구용 백업을 만들고 외장하드에 보관하는 구조로 설계한다. **현재 실제 외장하드는 없으므로 로컬의 지정 폴더가 외장하드 저장 경로를 대신한다.**

백업 파일 생성과 DB 복원·검증은 실제로 수행한다. 저장 장치만 대신하는 것이므로 빈 파일이나 성공 문구만으로 시연하지 않는다. 외장하드를 확보하면 저장 경로 설정을 변경하고, 접근 권한·여유 공간·연결 상태를 확인하는 방식으로 확장한다.

현재 실습으로 검증할 수 있는 것은 백업·복원 기능이다. 같은 PC에 저장한 파일로 PC 전체 손실이나 디스크 고장에 대비했다고 주장하지 않는다. 실제 외장하드 연결·분리와 물리 장치 장애도 아직 검증하지 않은 항목이다.

### 9.2 백업 단위와 정합성

**메타DB, A, B, C를 하나의 복원 세트로 관리한다.** 메타DB의 소유권과 실제 주문 위치가 맞아야 하기 때문이다. 서로 다른 시점의 매핑과 주문 덤프를 임의로 조합하지 않는다.

`pg_dump`는 개별 DB의 일관된 스냅샷을 만들지만, 여러 DB의 스냅샷 시점을 자동으로 맞추지 않는다. 따라서 이 프로젝트에서는 백업 동안 변경을 통제하는 간단한 방식을 제안한다. [PostgreSQL SQL Dump 공식 문서](https://www.postgresql.org/docs/18/backup-dump.html)

1. 재배치와 백업이 동시에 시작되지 않도록 공통 진입 제어를 확보한다. 미완료 재배치가 있으면 먼저 안전하게 복구·정리한다.
2. 모든 버킷의 새 쓰기와 매핑·스키마 변경을 제한하고, 진행 중인 변경 트랜잭션이 끝났는지 확인한다. DB 직접 수정도 이 시간에는 허용하지 않는다.
3. 변경이 멈춘 상태를 유지하며 메타DB와 A·B·C 덤프를 생성한다. 읽기는 이 조건을 깨지 않는 범위에서 허용한다.
4. 네 덤프의 성공 여부, 파일과 해시, 메타정보를 확인하고 한 세트로 완료 기록을 남긴다.
5. 성공·실패를 기록하고 제어 상태를 안전하게 해제한다. 중단 후에는 미완료 백업을 성공으로 취급하지 않는다.

이 방식은 백업 중 전체 쓰기가 제한되는 비용이 있다. 구체적인 주기와 실행 시간은 데이터 규모와 측정 결과를 보고 정한다. 백업 도중 C가 끊기거나 디스크 공간이 부족하면 **완전한 세트 생성 실패**로 처리하고 이전 정상 백업을 유지한다.

### 9.3 파일 구성 제안

`BACKUP_ROOT`와 `INCIDENT_ROOT`처럼 저장 위치를 설정으로 분리한다. 실제 폴더명과 설정 키는 구현할 때 확정한다. 아래는 디렉터리 구조 예시이며 아직 생성된 백업 파일이 아니다.

```text
<BACKUP_ROOT>/
  <backup-set-id>/
    metadata.dump
    shard-a.dump
    shard-b.dump
    shard-c.dump
    manifest.json

<INCIDENT_ROOT>/
  <incident-id>/
    incident.json
    application.log
    database-logs/
    metadata-state.json
    readable-databases/
```

백업은 `pg_dump`의 custom 형식(`-Fc`)과 `pg_restore` 사용을 제안한다. 파일 생성 명령과 Windows에서 안전하게 파일을 쓰는 방법은 구현 단계에서 한 줄씩 설명한다. [pg_dump 공식 문서](https://www.postgresql.org/docs/18/app-pgdump.html)

백업 명세에는 세트 ID, 변경 제한 구간과 생성 시각, DB·도구·스키마 버전, 해시 규칙·버킷 수, 매핑 버전, 파일 목록·크기·체크섬, 데이터 검증 기준, 완료 여부를 담는다. **파일 생성 완료와 실제 복원 검증 완료는 별도 상태로 기록한다.**

DB 역할·권한 등은 개별 DB 덤프만으로 모두 복구되지 않는다. 계정·권한 재생성 스크립트와 비밀값을 제외한 설정 예제를 함께 관리하고, 복원할 때 비밀값을 별도로 공급하는 방안을 사용한다. 구체적인 소유권·권한 복원 옵션도 함께 검증한다. [PostgreSQL 클러스터 전역 객체 백업 설명](https://www.postgresql.org/docs/18/backup-dump.html)

백업과 장애 자료는 Git에 올리지 않는다. 현재 프로젝트가 OneDrive 아래에 있으므로 실제 저장 경로는 동기화 여부까지 확인해 별도로 정한다. `.gitignore`는 클라우드 동기화를 막는 설정이 아니다.

### 9.4 복원 검증과 보존 정책

실습에서는 원본 DB를 덮어쓰지 않고 **별도의 테스트 DB·볼륨**에 백업 세트를 복원한다. 역할·권한을 준비하고 메타DB와 A·B·C를 복원한 뒤 다음을 확인한다.

- 매핑된 소유 샤드에 주문이 있으며 해시·버킷 값이 일치하는지.
- 주문 ID, 건수, 필드 내용과 검증용 체크섬이 백업 기준과 일치하는지.
- 테스트용 연결 설정으로 조회·라우팅·CRUD가 정상인지.
- 복원 소요 시간과 백업 이후 복구되지 않는 데이터 범위가 얼마인지.

기본 복구 목표는 **마지막으로 성공한 정상 백업의 데이터 상태**다. 그 이후 변경은 유실될 수 있다. 손실 없는 복구, 임의 시점 복구, 자동 장애 전환은 이번 기본 범위에 추가하지 않는다.

백업 주기, 보관 개수·기간, 자동 실행 방식, 허용 가능한 데이터 손실 시간과 복원 시간은 아직 미정이다. 실패한 새 백업 때문에 마지막 정상 백업을 삭제하지 않는 원칙을 둔다.

## 10. 장애 대응: 로그와 덤프를 별도로 남기기

### 10.1 무엇을 남기는가

장애가 발생하면 정상 백업과 다른 위치·식별자로 다음 자료를 남긴다.

| 자료 | 목적과 수집 조건 |
| --- | --- |
| 장애 발생 시각, 작업·요청 식별자, 오류 내용 | 어떤 동작에서 실패했는지 추적 |
| 애플리케이션 로그 | 요청, 예외, 연결 실패, 재배치 진행 과정 확인 |
| 접근 가능한 DB 로그 | DB 종료·재시작·SQL 오류 등 확인 |
| 접근 가능한 매핑·작업 상태 | 현재 소유권, 단계, 체크포인트, 마지막 검증 결과 확인 |
| 접근 가능한 DB의 장애 시점 덤프 | 장애 당시 데이터 상태 분석 |
| 수집 실패 기록 | 어떤 장비·DB의 자료를 왜 확보하지 못했는지 구분 |

**DB가 살아 있고 읽을 수 있어야 DB 덤프를 만들 수 있다.** C 전원이 꺼지거나 네트워크가 단절되면 즉시 C 덤프를 확보할 수 없다. 복구 후 수집한 자료에는 실제 수집 시각을 기록하며 장애 순간의 스냅샷인 것처럼 설명하지 않는다.

장애 시점 덤프는 이미 잘못된 데이터나 삭제된 상태를 포함할 수 있다. 정상 백업을 대체하거나 덮어쓰지 않는다. 로그·덤프에 비밀번호, 토큰, 불필요한 데이터가 남지 않도록 수집 범위와 접근 권한을 정한다.

앞서 논의한 “시스템 덤프” 중 운영체제 메모리·코어 덤프는 진단 자료다. **OS 전체 메모리 덤프 자동 수집은 현재 확정 기능이 아니다.** 이번 기본 계획은 애플리케이션·DB 로그, 상태 기록, 가능한 DB 덤프를 우선한다.

### 10.2 장애 종류에 따라 복구 방법을 구분한다

| 상황 | 우선 대응 | 복구 기준 |
| --- | --- | --- |
| 복사 중 애플리케이션 종료 | 상태와 실제 데이터를 확인하고 재실행 | 전환 전에는 출발 샤드가 기준 |
| 목적지 커밋 후 체크포인트 기록 전 종료 | 같은 배치를 비교·검증하며 재실행 | 이미 복사된 행과 충돌하는 내용 구분 |
| 소유권 전환 직후 종료 | 메타DB 커밋 결과와 목적지를 확인 | 전환 후에는 도착 샤드가 기준 |
| 출발 샤드 정리 중 종료 | 소유권을 확인하고 해당 버킷만 정리 재개 | 목적지의 새 데이터 보존 |
| C 연결 단절·장비 종료 | 관련 요청 실패를 명확히 알리고 자료 수집 | 연결 복구 후 상태 검증; 임의로 A·B에 쓰지 않음 |
| 메타DB 접근 실패·상태 모순 | 소유권 판단이 필요한 요청 제한 | 소유권을 추측해 계속 처리하지 않음 |
| 실제 데이터 손상·유실 | 영향 범위 평가, 정상 백업 확보 | 일관된 백업 세트로 복구 후 검증 |

재시작 시 복구 판단이 끝나기 전에 관련 변경 요청을 재개하지 않는다. 전환 후 목적지에서 새 쓰기가 일어났다면 오래된 출발 데이터를 덮어쓰지 않는다. 응답이 끊겼다는 이유만으로 DB 쓰기가 실패했다고 단정하거나 변경 요청을 무조건 재시도하지 않는다.

장애마다 전체 백업을 되돌리는 것은 아니다. 중단된 재배치는 현재 상태와 체크포인트로 재개하고, 데이터 자체를 잃은 경우에 백업 복원을 검토한다. 전체 백업 복원은 다른 정상 버킷의 최근 변경까지 되돌릴 수 있으므로 영향 범위를 먼저 설명한다.

장애 감지·수집을 어디까지 자동화할지와 수집 실패 후 재시도 정책은 별도 작은 작업에서 정한다. 꺼진 프로세스가 자기 자신의 모든 장애 자료를 자동 수집할 수 있다고 가정하지 않는다.

## 11. 검증과 실험의 완료 기준

| 검증 영역 | 완료를 판단할 증거 |
| --- | --- |
| 해시·라우팅 | 고정 입력의 버킷 일치, 매핑에 맞는 실제 DB 저장 |
| 주문 CRUD | 정상·오류 입력, 실제 행 변경·삭제, 사용자 범위 확인 |
| 전체 조회·집계 | 이동 중 복사본 중복 제외, 정렬·페이지 처리, 부분 실패 처리 |
| 정상 재배치 | 이동 전후 주문 ID·내용 일치, 소유권 전환, 이전본 정리 |
| 중단 후 복구 | 복사·검증·전환·정리 단계별 중단 후 안전한 재개 |
| 백업·복원 | 네 DB의 백업 세트 생성과 별도 DB에 실제 복원·검증 |
| 백업 실패 | C 단절·공간 부족 등에서 실패 표시, 기존 정상 세트 보존 |
| 장애 기록 | 수집한 자료와 수집하지 못한 자료를 구분한 기록 |
| 권한 | 조회자와 관리자 권한을 서버에서도 검사 |
| 두 장비 실험 | 실제 C 연결, 장비 종료·재시작, 정확성과 성능 측정 |

API의 성공 메시지만으로 검증하지 않는다. 별도 SQL 또는 검증 프로그램으로 실제 DB를 비교한다. 체크섬은 정렬, 금액, 시간대, NULL, 필드 구분 규칙을 고정하고 행 내용 비교와 함께 사용한다. 검증 도구가 구현 코드를 그대로 호출하는 것만으로 독립 검증을 주장하지 않는다.

성능 실험은 동일한 데이터·요청 조건에서 재배치 전·중·후를 비교한다. 균등 요청, 특정 버킷 집중, 한 사용자 집중을 구분한다. 버킷별 건수·요청량, 샤드별 자원 사용, 중앙값·p95, 처리량·오류율, 이동 시간·쓰기 제한 시간을 기록한다. 거부되거나 실패한 요청도 분모와 결과에 포함한다.

공용 PC의 다른 프로그램과 사용자 작업이 측정에 영향을 줄 수 있으므로 장비 사양·백그라운드 부하·네트워크 조건도 기록한다. 데이터 건수, 요청률, 반복 횟수와 성능 목표치는 장비 확인 후 결정한다.

## 12. 학교 강의실 PC를 C로 사용할 조건

학교의 사용 규칙 안에서 다음을 확인한다. 세부 확인 방법은 채팅으로도 안내한다.

- Docker·WSL 또는 PostgreSQL 설치·실행과 필요한 재부팅을 허용하는지.
- 운영체제, CPU 구조, 메모리, 디스크 공간, 가상화 지원이 실행 환경에 맞는지.
- 재부팅·로그아웃·수업 종료 시 사용자 파일, WSL, 컨테이너 볼륨이 초기화되는지.
- 같은 PC와 계정을 실험 기간에 계속 사용할 수 있는지.
- 내 PC와 C 사이의 실제 통신 경로가 있으며 필요한 DB 포트를 허용하는지.
- 내부망의 장비 간 통신 차단, IP 변경, 자동 절전·종료·업데이트가 있는지.
- 컨테이너 이미지 다운로드, 로그 확인, 자료 보관과 실험 후 정리가 가능한지.

같은 학교 Wi-Fi에 연결했다고 통신이 보장되지는 않는다. 내 PC가 집에 있고 C가 학교에 있다면 학교 내부 IP만으로 접속할 수 있다고 가정하지 않는다. 같은 허용된 실습망에서 두 PC를 사용하는 방안을 먼저 검토하며, 외부 연결이 필요하면 학교가 승인한 연결 방법을 확인한다.

DB 접속은 필요한 장비·계정으로 제한한다. Docker 포트 공개, 호스트 방화벽, PostgreSQL의 수신 주소와 인증 규칙을 함께 확인한다. 방화벽을 통째로 끄거나 인터넷 전체에 DB를 공개하는 방식으로 해결하지 않는다. [PostgreSQL 접속 제어 공식 문서](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html)

Docker Desktop을 쓸 경우 설치 시점의 공식 Windows·WSL·하드웨어 요구사항을 확인한다. 최소 실행 사양 충족과 원하는 부하 실험 가능 여부는 별도로 판단한다. [Docker Desktop Windows 요구사항](https://docs.docker.com/desktop/setup/install/windows-install/)

학교 PC 조건이 맞지 않으면 로컬 기능 개발은 계속할 수 있다. 실제 다른 장비 실험을 유지할 수 있는 대체 장비·장소는 팀과 다시 정한다.

## 13. 범위와 한계

기본 범위에는 입력 검증, SQL 파라미터 바인딩, 비밀정보 분리, DB 최소 권한, 사전 등록한 조회자·관리자 접근 제어, 백업·복원 검증을 포함한다. 관리자 권한은 화면 버튼만 숨기는 방식으로 구현하지 않는다.

다음은 기본 범위에 포함하지 않는다.

- 실제 회원가입·결제·재고 관리 서비스.
- 완전 자동 부하 예측·재배치와 운영 중 동적 버킷 분할.
- 한 사용자의 주문을 별도 규칙으로 여러 샤드에 분할하는 기능.
- CDC·이중 쓰기를 이용한 무중단 쓰기 재배치.
- 다중 애플리케이션 서버, DB 자동 복제·장애 전환.
- Redis, Kafka, Kubernetes 등 별도 분산 인프라.
- WAL 기반 임의 시점 복구와 OS 전체 메모리 덤프 자동화.

## 14. 개발 순서와 한 번의 작업 크기

아래 순서는 전체 로드맵이다. **표의 한 행을 한 번의 요청으로 전부 구현하지 않는다.** 사용자가 지정한 작은 작업만 구현·설명·검증하고 다음 요청을 기다린다.

| 큰 흐름 | 작게 나누는 작업 예시 |
| --- | --- |
| 요구·설계 정리 | 용어 정리 → 한 테이블의 컬럼 → 제약조건 → 해시 명세 |
| 로컬 DB 준비 | PostgreSQL 한 개 실행 → `SELECT 1` → 테이블 한 개 → 연결 한 개 |
| 주문과 라우팅 | 주문 한 건 저장 → 해시 함수 → 매핑 조회 → 샤드 선택 → CRUD 각각 |
| 분산 조회 | 전체 건수 → 소유 버킷 필터 → 정렬 → 페이지 처리 → 실패 처리 |
| 재배치 | 쓰기 제한 → 한 배치 복사 → 체크포인트 → 검증 → 전환 → 정리 |
| 중단 복구 | 중단 지점 하나 재현 → 상태 판별 → 안전한 재개 → 독립 검증 |
| 보안·백업·장애 자료 | 권한 하나 → 덤프 하나 → 일관된 세트 → 복원 → 장애 자료 수집 |
| 두 장비 실험 | 학교 PC 조건 확인 → C 연결 → 한 버킷 이동 → 장애·성능 측정 |
| 화면·발표 | 검증된 API부터 React 화면 구성 → 시연과 설명 연습 |

설명은 채팅에도 남긴다. 매 작업에서 목적, 바꾼 코드·SQL의 각 구문, 명령을 실행할 위치와 의미, 기대 결과, 실제 검증 결과를 연결해서 설명한다. 문서 링크만 전달하고 설명을 생략하지 않는다.

## 15. 2인 팀 협업 방식

팀원의 숙련도와 사용 가능한 시간을 확인한 뒤 역할을 나눈다. 재배치 핵심 흐름은 두 사람이 함께 이해하고 서로 설명할 수 있어야 한다. 아래는 배정 후보이며 아직 담당자를 확정한 것은 아니다.

| 팀원이 맡기 좋은 작업 | 전달할 내용 | 완료 조건 예시 |
| --- | --- | --- |
| 헬스 체크 응답 보완 | 현재 컨트롤러·테스트, 합의한 필드와 기존 응답 호환 조건 | 응답과 테스트가 함께 일치 |
| 테스트 주문 생성기 | 해시 명세, 데이터 형식, 건수·시드 입력 | 같은 시드로 같은 데이터 생성, 해시 벡터 통과 |
| 독립 검증 도구 | 테이블 명세, 소유권 규칙, 비교 항목 | 의도적으로 만든 유실·중복·내용 차이 검출 |
| 장애 로그 수집 기능 | 수집 대상, 실패 처리, 비밀정보 제외 규칙 | 일부 DB가 꺼져도 수집 결과와 실패 이유 기록 |
| 학교 PC 조사·실험 기록 | 이 문서의 장비 조건과 측정 항목 | 허가·보존·통신 가능 여부와 재현 절차 기록 |

작업을 넘길 때 대상 파일, 입력·출력, 수정 범위, 선행 작업, 테스트와 완료 조건을 함께 전달한다. 팀원에게 맡긴 코드를 먼저 대신 완성하지 않는다. 작은 변경 단위로 Git에 기록하고 상대가 검토·실행한 뒤 합치는 방식을 준비한다.

## 16. 다음에 결정할 사항

1. 학교 PC 사용 허가, 데이터 초기화 정책, 내 PC와 C를 연결할 장소·망.
2. 두 사람의 역할, 실제 제출일, 작업 가능한 시간과 최소 시연 범위.
3. 해시의 정확한 명세와 버킷 저장·검증 방식.
4. 상세 DDL, 주문 상태·금액 범위, API 경로와 오류·재시도 계약.
5. 재배치 상태 이름, 배치 크기, 대기 시간 상한과 연결 풀 설정.
6. 백업 실제 저장 경로, 주기·보존 정책, 복구 목표, 자동 실행 범위.
7. 장애 자료 수집의 자동화 범위와 보관·정리 기준.
8. 실험 데이터 규모와 부하 조건, 반복 횟수.

이번에 확정한 핵심은 **정상 시점의 복구용 백업을 외장하드 대체 폴더에 보관하고, 장애 시에는 로그·상태·가능한 덤프를 따로 남기는 것**이다. 세부 구현은 이 계획을 기준으로 작은 단위로 설명하며 결정한다.
